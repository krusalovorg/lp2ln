# LP2LN — архитектурный аудит передачи данных в реальном времени

**Дата аудита:** 24 ноября 2026 г.  
**Решение:** расширить существующий QUIC-транспорт и добавить логический `Flow` поверх аутентифицированных путей. Первый звонок — два телефона в LAN, QUIC DATAGRAM для голоса, отдельный надёжный канал управления и `lp2ln-rtc` как клиент публичного API. Следующий рубеж — один добровольный relay и смена пути с сохранением звонка. Критерий уровня качества Telegram — сравнительные замеры на устройствах и мобильных сетях после этого рубежа.

**Три блокирующих условия для первого звонка.** Android сейчас регистрирует TCP/UDP. QUIC ядра гонит обычные пакеты по одному bidirectional stream. Текущий packet path не даёт срока актуальности, строгого бюджета очереди и forward secrecy для сквозного шифрования. Для MVP требуется узкий новый путь данных с явной аутентификацией и ограниченными очередями. Discovery, идентичность устройства, транспорт и жизненный цикл ноды можно переиспользовать. [Android, start_node](https://github.com/krusalovorg/lp2ln-android/blob/f318110f0a7075a2f0f71d01a7b6d7b04cd8b400/rust/src/lib.rs#L75-L101) · [приём QUIC stream](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/transport/quic/transport.rs#L213-L237) · [очередь обработки](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/router/dispatch.rs#L22-L56) · [существующий secure envelope](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/crypto/secure_channel.rs#L18-L54)

### Путь пакета

1. `NodeRuntime::send_with_options` формирует `Packet` с адресатом, payload, полями protocol/request ID и hop budget. Транспортный интерфейс даёт start/stop/dial и необязательные NAT hooks. `Session` получает `Packet` или сериализованный `Vec<u8>`, публикует `IncomingPacket` и классифицирует надёжность через `LinkKind`. [отправка](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/node/runtime/messaging.rs#L66-L99) · [Transport и TransportContext](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/transport/transport.rs#L68-L135) · [Session и LinkKind](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/sessions/session.rs#L7-L95)
2. `Router::send_to_peer` подготавливает шифрование/подпись, выбирает имеющуюся сессию адресата или соседа. Fallback предпочитает прогресс по XOR-расстоянию, затем использует порядок соседей по score. На Android pin fallback останавливается после первого успешного enqueue, а блоки и chunked packets требуют надёжный hop при действующем `DeliveryLimits`. Это локальное решение на hop, без подтверждения доставки адресату или резервирования маршрута. Ошибка отправки на текущую прямую сессию закрывает её и возвращает ошибку, а relay в этом вызове не пробуется. [прямая отправка и ограничения](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/router/router.rs#L259-L334) · [fallback](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/router/router.rs#L338-L423) · [DeliveryLimits](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/node/options/transport.rs#L106-L133)
3. Reader декодирует packet, Router считает ingress, выполняет dedup и сборку chunks. Dispatcher передаёт работу воркерам. `DefaultPacketProcessor` проверяет подпись и привязку первого hop, локально расшифровывает envelope и проверяет replay, затем обрабатывает control, доставляет или пересылает дальше. Воркеры допускают переупорядочение обработанного потока даже поверх ordered транспорта. [воркеры](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/router/dispatch.rs#L75-L112) · [ingress](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/router/dispatch.rs#L151-L207) · [аутентификация и доставка](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/packet_processor/processor.rs#L103-L232) · [передача на следующий hop](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/packet_processor/forwarding.rs#L6-L56)
4. На pin V4 сохраняет подпись автора при изменении `nodes/max_hops` relay-узлом. Android явно настраивает V4 и требует подписи. Core `main` содержит V3: подпись включает mutable hop-поля, а egress подписывает forwarded packet ключом пересылающей ноды, сохраняя исходный `sender`. Полностью подписанный relay через смешанный парк версий поэтому требует отдельной проверки. Локальная поддержка V4 у адресата не гарантирует её у промежуточного узла. На pin по умолчанию используется V3. Успешная проверка V4 запоминает эту возможность для peer. Для первого контакта через relay безопасную совместимость нужно согласовать явно. [egress main](https://github.com/krusalovorg/lp2ln/blob/ea204010d88a8fc24b089b8789fac5775cc0737f/crates/lp2ln-core-v2/src/router/egress.rs#L45-L70) · [подпись main](https://github.com/krusalovorg/lp2ln/blob/ea204010d88a8fc24b089b8789fac5775cc0737f/crates/lp2ln-core-v2/src/crypto/signature.rs#L24-L85) · [V3 и V4 на pin](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/crypto/signature.rs#L8-L85) · [egress pin](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/router/egress.rs#L49-L81) · [Android V4](https://github.com/krusalovorg/lp2ln-android/blob/f318110f0a7075a2f0f71d01a7b6d7b04cd8b400/rust/src/lib.rs#L79-L92)

## 4. Предлагаемая целевая архитектура

`Flow` — двунаправленный логический канал приложения до Peer ID. Он держит семантику доставки, контекст аутентификации, ключи и очереди. `Link` — защищённое соединение с ближайшим узлом. `Path` — один или несколько hops от отправителя к адресату, с явной проверкой пригодности для требований Flow. При замене Path состояние Flow сохраняется. Один активный путь на поток достаточен для MVP. VPN может передавать IP datagrams, игра — состояния и команды, файлы и вычисления — надёжные сегменты. Core оперирует доставкой и квотами для всех этих сценариев.

~~~mermaid
flowchart TD
    App["RTC / VPN / игра / передача файлов"] --> Flow["Flow — доставка, очередь, E2EE"]
    Flow --> Sched["Scheduler — приоритет, pacing, TTL"]
    Sched --> Direct["Прямой проверенный link"]
    Sched --> Relay["Путь через relay с квотой"]
    Relay --> Peer["Удалённый Flow"]
    Direct --> Peer
    Disc["LAN, адресная книга, DHT, NAT"] --> Paths["Выбор и верификация пути"]
    Paths --> Sched
    Peer --> Paths
~~~

### Профили доставки

| Профиль | Доставка и порядок по умолчанию | Поведение при перегрузке | Примеры |
|---|---|---|---|
| `Reliable` | Надёжная, ordered внутри flow. Без TTL по умолчанию. Сбой виден вызывающему коду, а успех на удалённом конце подтверждается по контракту. | Bounded wait и byte credits, cancellation и timeout возвращают ошибку. | Команды, signaling, текстовый чат. |
| `Realtime` | Unreliable, unordered, обязательный TTL и положительный бюджет очереди, selective retry позже при наличии временного запаса. Только при явной политике можно вытеснить живое сообщение, по умолчанию для live audio лучше новое. | Двусторонний звук и видео, позиция в игре, телеметрия. |
| `BestEffort` | Unreliable, unordered, небольшой лимит очереди, TTL опционален. | Допускается отбрасывание и pacing с малыми затратами. | Необязательные updates, пробы с отдельным бюджетом. |
| `Bulk` | Надёжная, ordered в v1, возобновление на границе независимых сегментов прикладного протокола. | Использует свободную ёмкость, окно и byte credits ограничивают активные данные. | Блоки, резервные копии, задания вычислений. |

Надёжность и порядок независимы в контракте. `Unreliable + Sequenced` отбрасывает запоздало пришедшие старые состояния. `Unreliable + BoundedOrdered` потребует ограниченного reorder window и явного перехода через пропущенный номер к deadline. `Reliable + Unordered` можно добавить через независимые сообщения или независимые streams без общего reorder. На v1 неподдерживаемые сочетания возвращают `UnsupportedDelivery`. Для bounded reliability отдельный результат `Expired`, бесконечная retransmission с deadline несовместима. Передача in-order по конкретному stream даёт порядок только внутри flow и только пока не выбрана семантика reset/resume.

**Transport selection.** Путь пригоден, если на всех hops согласованы режим, требуемые возможности, MTU, лимиты и admissible security. Выбор зависит от фактических задержек и доступности. Прямой LAN выигрывает при сравнимом качестве. TCP/QUIC streams подходят для reliable, QUIC DATAGRAM для realtime и best effort. Raw UDP в будущем потребует общего demux, аутентифицированного handshake, MTU discovery, feedback, pacing и congestion control. Нового транспорта для первой версии не нужно: расширить `Session` необязательным интерфейсом `FlowLink` и сохранить `Transport` для lifecycle. Отдельный TCP connection или stream снижает локальную конкуренцию, TCP retransmission всё ещё задерживает live payload. В MVP, если доступен только TCP, signaling может работать, а media Flow возвращает `NoCompatiblePath`. [Transport](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/transport/transport.rs#L94-L135) · [Session](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/sessions/session.rs#L54-L95) · [RFC 9221](https://www.rfc-editor.org/rfc/rfc9221.html)

**Quinn.** Явно настроить send/receive datagram buffers, проверять `max_datagram_size()` и использовать `read_datagram()`/`send_datagram(Bytes)`. Очередь Quinn может вытеснять более старые datagrams при переполнении, а `send_datagram_wait` ждёт места и оставляет приоритет за старой очередью. `datagram_send_buffer_space` помогает наблюдать давление, но не означает, что congestion window или радио готовы передать пакет. Сначала установить малый общий byte buffer и application-level shallow queues, считать отдельно «принято в Quinn», «отправлено на socket» при доступной телеметрии и «получено приложением». Для reliable использовать отдельные streams, `SendStream::set_priority` и ограниченные chunks. Stream priority не задаёт взаимный приоритет datagrams и streams. Нужен бюджет подачи в общую QUIC connection и проба поведения под contention. RFC 9221 не ретранслирует DATAGRAM и применяет QUIC congestion control. Для закреплённых Android/Core версий подтвердить настройки контрактными тестами. [Quinn Connection 0.11.6](https://docs.rs/quinn/0.11.6/quinn/struct.Connection.html) · [Quinn Connection 0.11.11](https://docs.rs/quinn/0.11.11/quinn/struct.Connection.html) · [Quinn SendStream](https://docs.rs/quinn/0.11.6/quinn/struct.SendStream.html) · [RFC 9221](https://www.rfc-editor.org/rfc/rfc9221.html)

**Срок актуальности.** На входе производителя фиксировать capture/created time по монотонным часам. Проверять возраст при enqueue, dequeue, перед транспортом и перед отдачей в приложение. Таймер очищает очередь даже при отсутствии нового трафика. Relay имеет локальный предел ожидания и bounded queue. Сквозной deadline передаётся в E2E-аутентифицированном заголовке. Для удалённой проверки нужен интервал оценки смещения монотонных часов из authenticated timestamp exchange с запасом на RTT, асимметрию, дрейф и suspend. Выдавать кадр, только если верхняя оценка его возраста укладывается в TTL. При отсутствии надёжного интервала strict mode приостанавливает доставку и перепроверяет часы. Optional local-only режим следует маркировать отдельно. Удалённая проверка не предполагает согласованные wall clocks. Quinn v1 не предоставляет отзыв отдельного уже принятого datagram по deadline. Снижаем риск запоздалой отправки bounded admission и проверяем фактический queue age на тестах. Если критерий «ни одного просроченного кадра на wire» станет обязательным, понадобится механизм expiry внутри transport scheduler. Просроченный realtime не ждёт в прикладных очередях и не выдаётся приложению.

**Планировщик и fast path.** Хранить на Flow заранее разрешённый handle пути. Менять его при обновлении состояния, без clone списка соседей на каждый кадр. Развести reserved control, latency-sensitive и bulk. Внутри realtime учитывать deadline и admission-weight, выдавать fairness между peers, ограничить приоритет, который может запросить приложение. Bulk выдавать по byte credits/deficit round robin после резервов, с минимальным прогрессом при доступной полосе. Пейсинг адаптируется к delivered goodput и перегрузке с учётом протокольных bytes. QUIC CC остаётся нижним контуром. Для relay вдобавок нужен E2E feedback, поскольку соседнее QUIC соединение видит только свой hop. Общий budget в байтах и pps на ноду, peer и flow перекрывает риск множества мелких frame-ов. Буферы `Bytes/BytesMut` и AEAD in-place с head/tail room, короткие bounded headers, счётчики пакетами, batched JNI по готовности. Batching не ждёт заполняемости и ограничивается deadline. Memory pool и lock-free оптимизации вводить по профилю. Отдельные datagram и reliable очереди делят CPU и радио, поэтому проверить планировщик при насыщенном bulk в обоих направлениях.

### Self-Optimizing Connectivity

1. **Обнаружение.** Один менеджер кандидатов объединяет PeerDirectory/LAN, cached endpoints, подписанные descriptors/DHT, наблюдаемые адреса и добровольные relays. Кандидат хранит peer, источник, срок жизни и network epoch. Отказавшие адреса получают jittered exponential backoff. Смена сети открывает новый epoch. Использовать текущие state transitions и dial book. Для LAN MVP нужны ручной QR/import peer + endpoint и signed multicast с проверкой исходного интерфейса. [ranked_dial_targets](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/node/direct_upgrade/addrs.rs#L109-L162) · [существующий backoff](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/node/link_survival/scoreboard.rs#L83-L165)
2. **Проверка.** Staggered race с ограничением параллелизма и общего времени, например 2–3 активных кандидата и 50–150 мс начального stagger на интерактивном open, после измерений. Сначала получить ответ на свежий challenge от ожидаемого peer через конкретный link, затем E2E response на пробу для пути и всего своего маршрута. Закрывать проигравшие сессии, кроме одной проверенной запасной при наличии активного Flow и бюджета. Путь адресуется локальным network epoch, типом carrier, удалённым peer, candidate/relay chain. Вынести verified race из bootstrap-specific вызова в общий управляющий слой. [bootstrap racer](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/node/topology_maintenance/dialing.rs#L221-L303) · [текущая проверка и cleanup](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/node/link_survival/racer.rs#L89-L179)
3. **Измерения.** Отдельно link RTT/QUIC stats и path end-to-end RTT, RTT variation или inter-arrival jitter, loss по sequence/feedback с reorder grace, late loss и delivered goodput. Для one-way delay — только синхронизированный стенд или явно оценённая погрешность. Свободную полосу оценивать из delivery-rate/queue delay при реальной нагрузке и короткими bounded trials. На малом аудиопотоке goodput — нижняя граница, помечать capacity unknown. Не ранжировать по географии или системному traceroute. Использовать факты data/ACK там, где они есть. Сводить частые измерения в EWMAs и histograms с age/confidence, проверять sender/receiver в обоих направлениях и различать relay/last mile.
4. **Выбор и стабильность.** Сначала фильтровать authentication/MTU/capabilities/budget. Для остальных минимизировать нормализованную стоимость RTT, jitter, late/loss, queue age, дефицита goodput и penalty нестабильности. Веса берёт профиль. LAN/direct — tie-break при сопоставимом качестве. Стартовый hysteresis на живом path — выигрыш ≥20% и ≥15 мс для метрики задержки там, где она определяет решение, три последовательных окна проверки, минимум 5–10 с после предыдущего планового переключения. Для групп вроде игр подбирать пороги по собственной телеметрии. Смерть или уход network epoch обходит dwell time. Сомнительную оценку не брать за основание для планового switch.
5. **Make-before-break.** `Active → Probing → StandbyVerified → Switch → Drain`, при потере `Degraded → Reconnecting/Standby → Active`. Новому пути выдать свежий аутентифицированный nonce/probe, проверить MTU, оба направления и привязать к существующему Flow. Commit смены с монотонным route generation выполнить согласованно, старый путь кратко держать для drain/reorder. Шифрование и номера кадров независимы от пути. При временной недоступности сохранять логический handle и capped состояние на короткий срок. Кадры realtime истекают. Reliable control на v1 сообщает о потере соединения, signaling делает idempotent retry. P1 добавляет scoped ACK/resume для гарантии логической доставки. Таймер восстановления даёт приложению явное завершение.
6. **Частота.** Стартовые параметры P1: под активным трафиком E2E feedback агрегировать примерно каждые 0,25–1 с, при тишине до 1 отдельной пробы/с на активном пути и реже на standby. Без Flow ограничиться существующим topo/idle профилем. Ослаблять probing на батарее и metered network, короткий burst по смене сети или деградации, backoff после неудач, общий pps/byte budget. Keepalive relay lease/NAT забивает только нужный минимум по наблюдаемому таймауту. Активная лёгкая проверка пути и topology watchdog работают на разных временны́х масштабах. [текущие таймеры](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/node/link_survival/watchdog.rs#L48-L112)
7. **Multipath позже.** P2 допускает два независимых paths, короткий дедлайн и копию отдельных кадров в неперекрывающихся failure domains. Дубль — тот же ciphertext и seq, отдельное начисление bytes. Ограничить, например, до 5% дополнительного трафика на окно и отключать при congestion/общем bottleneck. Начать с единичных критичных фреймов и измерить выигрыш по late-loss. FEC/media-specific стратегия остаётся на уровне приложения. Непрерывное striping требует отдельной оценки fairness, reordering и платы за держание обоих интерфейсов.

**Текущая цепочка NAT.** `NatOffer → NatAnswer → NatPunchStart → NatPunchResult` реализована как control/state machine. Задание выполняется по UDP-кандидатам. STUN при занятом порте пробует ephemeral socket, поэтому наблюдаемый mapping может не принадлежать data socket. Punch принимает ответ по совпадению адреса и не служит доказательством identity. Условия используемого маршрута control управляются Router, который проверяет его тип уже после egress sealing. Отдельный tested формат consent/rendezvous нужен для cold contact через relay. [NAT control handlers](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/packet_processor/control.rs#L145-L186) · [состояния и очередь punch](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/nat/mod.rs#L107-L193) · [STUN socket](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/stun/client.rs#L29-L55) · [punch](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/transport/udp/transport.rs#L275-L341) · [control classifier](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/router/router.rs#L278-L306)

| Сетевой сценарий | Как работает целевой вариант |
|---|---|
| Один Wi-Fi без интернета | LAN HELLO или ручной QR с Peer ID и endpoint, прямой защищённый QUIC. DNS/STUN/bootstrap опциональны и не стоят в критическом пути. Если AP изолирует клиентов, нужен другой reachable путь, например hotspot. |
| Публичный интернет, прямой путь | Signed descriptors или адресная книга, IPv4/IPv6 candidates, verified race, прямой path при подходящем качестве. |
| NAT / CGNAT | Параллельная проверка host и server-reflexive кандидатов, STUN на том же UDP socket, который держит mapping, ICE-подобные authenticated checks, peer-reflexive candidates и nomination. Подходящий relay подключается параллельно при сложном NAT. STUN наблюдает адрес, а не гарантирует проходимость. Текущий punch не является ICE и не устанавливает QUIC. [ICE RFC 8445](https://www.rfc-editor.org/rfc/rfc8445.html) · [STUN RFC 8489](https://www.rfc-editor.org/rfc/rfc8489.html) · [TURN RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html) |
| Интернет с одним relay | Bounded добровольный relay с short lease и двухсторонним admission. Две QUIC-связи несут ciphertext Flow. Нода может одновременно играть роль bootstrap, но bootstrap identity и relay capability независимы. |
| Несколько relay | После P1 — ограниченная цепочка проверенных соседей с допуском на каждом hop, ceiling по hop count и path MTU. DHT/mesh даёт кандидатов, а end-to-end пробы подтверждают путь. |
| Bootstrap отказал | Работающие direct/relay пути сохраняются. Многосидовый конфиг, persistent peers, LAN и discovery через оставшихся соседей восстанавливают entrance. Для первого контакта двух пустых адресных книг нужен хотя бы один reachable seed, локальный discovery или внеполосный адрес. |
| Relay отказал / direct восстановился | Проверенный standby принимает Flow. При его отсутствии запускается bounded retry другой цепочки/прямого пути. Direct↔relay использует один механизм switch, повторное приглашение не требуется. |
| Изменился IP, Wi-Fi → LTE | Android передаёт событие и сетевой handle. Новые candidates/сокеты и path validation. Quinn `Endpoint::rebind` может помочь при смене локального сокета и достижимом peer, это операция уровня endpoint, не универсальная смена маршрута или relay. Отдельные endpoints при одновременной проверке интерфейсов. [QUINN Endpoint 0.11.6](https://docs.rs/quinn/0.11.6/quinn/struct.Endpoint.html) · [RFC 9000, migration](https://www.rfc-editor.org/rfc/rfc9000.html#section-9) |
| Транспорт блокирован | Проверка capability и реально доступных endpoints. Control/контент могут идти по TCP, media использует доступный datagram path, включая relay. Если ни одного пригодного media path нет, UI сообщает о деградации. TCP media fallback потребует отдельного измерения tail latency и явной политики деградации. |
| Полная потеря сети и короткий обрыв | `Reconnecting`, realtime не буферизуется на весь обрыв. После проверки нового маршрута передаются свежие кадры. При истечении watchdog окна звонок завершается. Без reachable маршрута входящий звонок и доставка невозможны. |

Rendezvous-сообщения идут между адресованными peers по проверенному существующему overlay либо прямому каналу. DHT оставляет подписанные, краткоживущие записи контакта, которым разрешено быть публичными. Бессрочные invitations и история звонков в DHT не нужны. Relay обслуживает транспорт и видит минимальную route metadata. Signaling и медиа расшифровываются у адресатов.

## 5. Изменения публичного API

Предлагаемая форма для embedded Rust. Имена и числа подлежат проверке в прототипе, а ошибки должны быть частью версионируемого контракта.

~~~rust
pub struct FlowOptions {
    pub profile: FlowProfile,
    pub delivery: Delivery,
    pub ordering: Ordering,
    pub priority: Priority,
    pub max_queue_delay: Duration,
    pub max_age: Option<Duration>,
    pub max_payload: usize,
    pub max_queued_bytes: usize,
    pub target_bps: Option<u64>,
    pub min_bps: Option<u64>,
    pub max_loss_ratio: Option<f32>,
    pub path_policy: PathPolicy,
}

let flow = node.flows().open(peer_id, protocol_id, options).await?;
let report = flow.try_send(payload, FrameOptions::new(created_at, ttl))?;
let incoming = flow.recv().await?;
~~~

- `FlowProfile::{Reliable, Realtime, BestEffort, Bulk}` задаёт defaults. `FrameOptions` может сократить срок, объявленный Flow. Caller не может продлить чужой negotiated budget. `PathPolicy` включает direct preference, разрешение relay/тарифицируемых сетей, max hops, max standby и later redundancy policy. Использовать валидируемые finite значения и различать требования admission и цели оптимизации. `min_bps` и `max_loss_ratio` требуют фактических данных или явного `PathUncertain`, а не обещаний.
- `register_protocol(protocol_id, policy)`, `accept()`, `open()`, `close()`. Явное входящее согласие, проверка supported profiles/version, ограничение открытых потоков по peer и приложению, освобождение при drop/cancel. В MVP idempotent open/close и stable session scope. Reliable `send().await` использует предел ожидания, `try_send()` для realtime быстро возвращает статус локального admission. `QueueFull`, `Expired`, `TooLarge{limit}`, `NoCompatiblePath`, `PeerUnsupported`, `QuotaExceeded` и `TransportClosed` различимы. «Принят к отправке» и «подтверждён получателем» — разные события.
- `FlowEvent` отдаёт `PathChanged`, `Degraded`, `Ready`, `Closed` и агрегированный `FlowStats`: RTT, jitter, loss, late-drop, feedback confidence, congestion, recv-goodput, queue ages, bytes charged, путь, max payload. Event delivery coalesced, приложение может snapshot. Transitions надёжны в пределах контракта.
- `Session` сохраняет текущие методы. Дополнить capability query или дочерним `FlowLink` с send/recv datagram и open/accept independent streams, max payload и link feedback. Default impl возвращает unsupported. На транспортном уровне отдельный frame enum/receiver для FLOW. На приложение кадры выходят только из authenticated Flow service.
- Android и Desktop embedded используют тот же API. IPC P2 добавляет `FlowOpen/FlowAccept/FlowData/FlowCredit/FlowStats/FlowClose` за отдельной negotiated capability, с correlation ID и byte budget на клиента. Зарегистрировать namespace или IDs в текущем app protocol. Локальный IPC credit и end-to-end credit различаются. `AppClient` нужно split reader/writer либо multiplex request IDs, чтобы ожидание ACK не блокировало двусторонний поток. ### Учёт ресурсов

`CapacityBudget` продолжает задавать пределы mesh, а фактические ресурсы Flow допускаются через локальную политику. Для relay lease запрашивает max bps/pps, max live flows, TTL, queue budget, max payload и authenticated owner. Политика по умолчанию для новых relays — явное согласие оператора. Admission проверяет ресурсы до выделения буферов и до дальнейшей переадресации, использует byte-token buckets на peer/relay/global, bounded control reserve и отказ `QuotaExceeded`. Несколько классов счёта: local owner, transit inbound/outbound, probe, retransmit, duplicate. Не приписывать payload bytes к wire bytes. Лимиты на подключение и обработку control защищают worker pool. Active reservation pin не отменяет физический ceiling и операторское отключение.

Хранилище и compute впоследствии подключаются к общей модели единиц `bytes/s, bytes×time, CPU time, memory×time` и к агрегированному `ResourceUsage`. Достаточно локальных counters и интерфейса read-only export/optional policy. Подтверждённая внешняя оплата может увеличить квоту по явному правилу оператора. Никакая внешняя система не участвует в обязательном datapath или авторизации личного/локального звонка. [существующие capacity fields](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/topology/capacity.rs#L6-L54) · [capability и status](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/topology/descriptor.rs#L13-L87)

## 8. Стратегия обратной совместимости

- Сохранить layout `Packet` и его postcard wire. Для Flow отдельный versioned frame namespace и capability negotiation. Обычные `Transport`/`Session` и legacy service работают с peers без Flow. Смена формата прежних структур, включая новые поля в postcard structs, требует отдельного wire compatibility теста. Использовать negotiated new control opcode, расширяемый envelope или отдельный ALPN только при необходимости несовместимого link handshake. Прежняя конфигурация listener остаётся доступной.
- Завести fixture для Core main, Core pin и новой версии. P0 интегрировать/версионировать два коммита pin с проверкой V3 прямого пути, V4 end-to-end через обновлённый relay, mixed-path отказа и restart sequence, Android file/chat, DHT и блоков. Upgraded peers должны явным образом доказывать поддержку Flow, включая каждый relay. Корректная ошибка `PeerUnsupported`/`NoCompatiblePath` позволяет оставить legacy-мессенджер рабочим.
- Отделить rollout версий wire и SDK: feature flag/negotiation, записывать выбранную версию, сохранять rollback назад на legacy-режим для приложений без Flow. Для звонков явное отсутствие поддержки вместо отправки медиа через старый `Packet`. Тестировать оба lock-профиля Quinn до их унификации.
- Текущий файловый путь и IPC streams оставить совместимыми. Переносить file chunks на `Bulk` по отдельному opt-in после gate времени/пропускной способности. Изменение неподписанной или pre-auth legacy подписки требует аудита её клиентов, прежде чем менять поведение.

## 9. Модель безопасности и потенциальные риски

**Границы существующей криптографии.** Secure envelope получает ключ из статического k256 ECDH с long-term identity, SHA-256 и ChaCha20-Poly1305 со случайным 96-битным nonce. Направления используют одинаковый derived key. Forward secrecy для payload этого механизма отсутствует. Seq лежит вне AEAD AAD, но обычная V3/V4 подпись защищает hash envelope при обязательной верификации. Replay window — 128 позиций на sender и in-memory. Новый egress Android pin резервирует исходящие sequence ranges в state file при наличии пути. Это помогает sender restart, но не сохраняет входящий replay state при restart адресата. Один глобальный счётчик отправителя и per-sender window допускают false late/replay при большом расстоянии между seq одновременно летящих пакетов. Ошибка replay в pin учитывается как ошибка сессии, поэтому новый Flow должен нормально переживать ожидаемые запоздания и дубли. [envelope и replay](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/crypto/secure_channel.rs#L12-L118) · [резервирование seq](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/router/egress.rs#L65-L138) · [инициализация router security](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/node/runtime/startup/orchestrator.rs#L84-L167) · [учёт отказов](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/packet_processor/processor.rs#L86-L100) · [replay на ingress](https://github.com/krusalovorg/lp2ln/blob/65925aaf9b8faabfba4f9eaf607ac5eb8860e0cc/crates/lp2ln-core-v2/src/packet_processor/processor.rs#L139-L174)

**Flow security.** Использовать reviewed authenticated ephemeral key exchange, например Noise с реализацией `snow` для handshake, либо end-to-end TLS 1.3 в соответствующем stream transport. Для единой direct/relay схемы выбрать ephemeral handshake, в котором сертифицированный существующим k256 device identity Noise key привязан к нужному peer, роли и согласованной версии. Взаимная проверка, domain separation и explicit key confirmation завершаются до отправки media. Спецификация должна обосновать подход к извлечению материала для unordered datagrams: стандартный ordered Noise TransportState нельзя просто применить к потере и переупорядочению. Использовать reviewed stateless/application record layer с независимыми направлениями и фиксированным wire nonce scheme. Согласовать crypto API и vectors в F2. Direct QUIC link дополнительно связывать с identity с помощью проверяемого сертификата либо подписанного fresh challenge, привязанного к TLS exporter и его transcript. E2E Flow handshake через relay связывается с путём посредством challenge на production data path. QUIC TLS завершается у ближайшего peer, E2E слой остаётся от отправителя до получателя. [Noise Protocol Framework](https://noiseprotocol.org/noise.html) · [RFC 9001](https://www.rfc-editor.org/rfc/rfc9001.html)

**Ключи и смена пути.** Из fresh ephemeral exchange получать ключи по session epoch и направлениям. Независимые seq по Flow и component либо общий уникальный nonce namespace с явно определённым разделением. AAD включает version/suite, FlowID, epoch, seq, semantic flags, endpoints/контекст transcript, ttl и метку времени. Authenticated immutable ciphertext не меняется в relay. Mutable hop data имеет hop-level integrity и потолки, а end-to-end delivery context подписан/защищён AEAD. Проверять tag перед commit replay window. Предфильтр может читать bounded header, но не повышает watermark до auth. Key rotation по времени/объёму или flow reopen, bounded overlap двух epochs, zeroize ephemeral secrets и retired keys. Для дублей на другом пути переотправляется тот же ciphertext без повторного seal. Path generation связывает управляющий switch и подтверждённый путь. Поздний кадр со старого пути допускается только в replay/deadline window. Выключить replayable 0-RTT для open/signaling/relay reservation и media. После рестарта нужны новые ephemeral keys, восстановление старого криптосостояния в MVP не допускается.

## 12. Минимальный путь до работающего голосового звонка 1 на 1

1. **Транспорт и соединение.** В Android зарегистрировать QUIC listen/dial, актуальный listener публиковать LAN Discovery и показать QR с peer+endpoint как воспроизводимый запасной вход. Оба телефона в foreground и без WAN, предварительно подтверждённые Peer ID. Через control lane отправлять `Invite/Accept/Reject/Cancel/Hangup` с expiry, random CallID, version, capabilities и idempotent ACK. При одновременных приглашениях фиксированный deterministic tie-break. Сигналинг получает адрес из Core и держит state machine внутри RTC. Отменённый или несогласованный invite не начинает capture.
2. **Звук.** `AudioRecord`/`AudioTrack` в режиме голосовой связи или WebRTC audio device/APM, Opus mono 48 кГц, кадры 20 мс, 16–32 кбит/с в фиксированном начальном профиле. 50 pps в каждую сторону. AEC/NS/AGC одним согласованным pipeline, jitter buffer 40–80 мс с ограниченным ростом, Opus PLC, позже DTX и in-band FEC по loss budget и допустимой задержке. Синхронизировать audio device clock и playout. Контролировать audio focus, earpiece/speaker/Bluetooth, задержку аудио output и headset changes. Opus оставляет место заголовкам: при 24 кбит/с 60 B payload/20 мс, каждый 100 B wire overhead добавляет 40 кбит/с в направлении. Реальный бюджет мерить на wire. [RFC 6716](https://www.rfc-editor.org/rfc/rfc6716.html) · [Android AudioTrack](https://developer.android.com/reference/android/media/AudioTrack)
3. **Библиотеки.** Для первого RTC полезен libopus и зрелый audio DSP на базе WebRTC APM. Полный WebRTC PeerConnection даёт проверенные media components и свой транспорт/ICE/адаптацию. Его можно использовать как сравнительный путь или browser adapter. Если завернуть весь PeerConnection, нельзя считать это проверкой Flow transport. Для MVP codec/APM подключить только один раз и измерить latency/ABI/package size, избегать пересечения платформенного AEC и APM. Design spike выбирает жизнеспособный способ использования Jitter Buffer/WebRTC без копирования media stack. [WebRTC API](https://www.w3.org/TR/webrtc/)

## 13. Минимальный путь до работающего видеозвонка 1 на 1

- Расширить `lp2ln-rtc` третьим Flow: reliable control, high-priority audio, lower-priority video. CameraX/Camera2 захватывает кадры, `MediaCodec` использует H.264 profile/level по общим возможностям и аппаратный Surface input/output. Базовый профиль для двух телефонов 360p, 15 fps, ориентир 250–500 кбит/с на направление при достаточной полосе. Начать без B-frames на поддерживаемом encoder или с low-latency mode после проверки device support. Аудио timestamps выступают playout clock для A/V sync. [Android MediaCodec](https://developer.android.com/reference/android/media/MediaCodec) · [Android media formats](https://developer.android.com/media/platform/supported-formats)
- Пакетизировать H.264 codec config и access units по проверенному правилу фрагментации, например использовать RTP payload semantics RFC 6184 внутри RTC. Validate seq, frame ID/PTS, size/count и caps. Oversize избегать adaptive max payload/packetization, неполное видео выбрасывать по deadline, не собирать в Core chunk assembler. Передавать SPS/PPS в согласованном control или повторять на ключевом кадре. При потере reference frame просить keyframe с rate limit. Медиа codecs и packetization остаются Android/RTC. [RFC 6184](https://www.rfc-editor.org/rfc/rfc6184.html)
- RTC оценивает budget из speed/loss/jitter/queue/late feedback. Резервирует аудио и control, режет bitrate видео, затем FPS/разрешение, при плохом uplink отключает видео, восстанавливает его с hysteresis. Не начинать новый keyframe burst, если он выталкивает аудио. В MVP вполне достаточно одной качественной ступени и audio-only downshift. Набор уровней и congestion tuning нужны для пилота.
- Desktop использует embedded Rust/SDK и OS capture. iOS подключает аудиосессию и capture, lifecycle/permissions по текущей политике OS проверяются отдельно. WebTransport даёт streams/datagrams до HTTP/3 server endpoint, которому нужен совместимый listener и доверенный браузером сертификат. Для browser P2P media практичен WebRTC adapter с ICE/DTLS-SRTP. Посредник для bridge может терминировать транспорт, поэтому E2EE проверяется отдельно. Если браузер и нативный клиент используют web gateway, он опционален для web и может обслуживаться несколькими операторами. [WebTransport](https://www.w3.org/TR/webtransport/) · [WebRTC](https://www.w3.org/TR/webrtc/)

## 14. Критерии готовности каждого этапа

Все числа ниже — **целевые стартовые пороги**, подлежащие подтверждению на описанном стенде. Указать hardware и carrier, иначе цифры несопоставимы.

| Рубеж | Gate |
|---|---|
| G0 · База и протокол | F0–F2: воспроизводимая release-сборка native и Android arm64, версия в логах, подписанный compatibility matrix, негативные тесты и bounded pre-auth. В 30-минутном нагрузочном тесте configured queue/memory counters не выходят за пределы. |
| G1 · LAN Flow | F3/M1: 50 pps в обе стороны, loss <1% в стабильном LAN, median RTT и jitter recorded, p95 network application-to-application ≤30 мс и p99 ≤60 мс при синхронизированном измерении, internal queue age p99 ≤20 мс при фоновой передаче. 0 late delivery и 0 duplicates на app. Без WAN/DNS setup через известных peers p95 ≤2 с, время discovery отдельно. |
| G2 · Голос | M2: два реальных Android, не менее 20 мин, screen-off, rotation/audio route/BT checks. p95 mouth-to-ear ≤180 мс в стабильном LAN, без отдельного freeze >200 мс на контролируемом LAN. Timer/queue не копят просроченные frames. Под bulk аудио сохраняет p95 в пределах +30 мс и bulk показывает прогресс. Ни один вызов на LAN не зависит от bootstrap. |
| G3 · Интернет и handoff | M3/M4: ≥95% установлений в матрице поддерживаемых путей с доступным relay, p95 setup ≤3 с при подключённом signaling, p95 switch-to-fresh-data ≤750 мс с verified standby, p95 ≤3 с при достижимом новом пути без standby в профиле стенда. FlowID и auth сохраняются, пригодные пути тестируются direct→relay→direct, есть controlled failure при отсутствии путей. |
| G4 · NAT и видео | M5/M6: NAT results по классам отдельно, symmetric CGNAT выполняет relay fallback. p95 glass-to-glass ≤350 мс в стабильном LAN на hardware codec, 360p/15 fps при достаточной полосе. 0,5 Мбит/с или 10% loss приводят к предсказуемому audio-first режиму, обязательные limits и размеры MTU соблюдены. |
| G5 · Оптимизация и публичный пилот | L1–L5 по мере надобности. Для выбранных телефонов публикуются PPS, CPU/PSS, Joules/мин (или измеримая оценка), доля времени аудио/video glitches и tail на 4G. Каждая оптимизация имеет A/B выигрыш и regression guard. Оценивать качество относительно сравнимого режима Telegram на том же оборудовании, без обещания паритета на всех сетях. |

**Порядок решения.** Зафиксировать базу Core/Android и контракты безопасности. Выпустить минимальный QUIC Realtime Flow, проверить его в duplex и под bulk, затем добавить Opus на двух телефонах. После подтверждённого LAN-голоса добавить один relay и устойчивую смену пути. Видеозвонок использует эту же транспортную основу и отдельное управление медиа.
